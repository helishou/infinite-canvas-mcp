# 审查、提交与发布

触发：PR 审查/处理、提交、发版本。继承[根约定](../../AGENTS.md)；用户可感知变更的文档职责见[docs/AGENTS.md](../../docs/AGENTS.md)。

## PR：分别判断需求与实现

| 结论 | 依据 |
|---|---|
| 需求价值 | 项目方向、用户场景、现有能力与后续规划；上下文不足时询问用户 |
| 实现质量 | 正确性、安全、范围、复用与重复代码、可维护性、相关测试/文档、与最新 main 的冲突 |

规模大、疑似批量生成或作者身份不能单独证明需求无价值；实现差也不等于需求不需要。需求有价值但实现不合格时，优先要求修改、提取思路重做，或保留 issue/todo。

可以在独立分支审查、修复、解决冲突并准备提交。合并进 main 前说明最终修复、验证、风险与冲突并取得明确同意；force-push 作者分支前说明影响并取得同意。已有对同一最终范围的授权不重复请求。

关闭 PR 前分别说明需求价值、实现质量、可保留思路和处理方式，并取得明确确认。批量关闭也逐项保留可判断的信息，不把关闭代码实现等同于否定需求。

## 普通交付与提交

- 只提交本任务范围的文件/改动；用户明确要求提交全部时按其范围执行。不要用 stash/reset/restore 清走工作区已有修改。
- 提交前看最终 diff 和相关检查结果；PR 描述写当前最终行为，不堆弃用方案和对话过程。
- 未授权的合并、发布或强推不因“代码完成”自动获得授权。所需审批留到实现与验证结果可审查之后。
- 汇报已完成结果、验证及实际未决项；不列无关检查，也不把尚未执行的验证写成通过。

## 用户要求发版本时

1. 将 CHANGELOG 的 Unreleased 归纳到新版本，保留空的 Unreleased 标题。
2. 按当前版本提升一个版本并更新根 VERSION，延续当前版本号格式。
3. 按项目发版约定，将当前未提交代码全部纳入提交；先核对清单，避免漏掉已有用户改动或纳入临时产物。
4. 提交完成后，在该提交打对应版本 tag，例如 v0.0.5；核对 VERSION、变更记录、commit 与 tag 一致。
5. 纯发版流程不编译、不测试、不构建，除非用户明确要求。若任务还包含代码修改，该修改的验证与产物准备在进入发版步骤前完成。

本流程不自动包含远端 push、托管平台 release、部署或清理旧数据；这些按用户实际要求执行。
