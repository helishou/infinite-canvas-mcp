# 编排预算与实测基线

快闪 PV 的墙钟时间大部分不在生成，也不在画布或 MCP，而在**每次调用之间的 AI 回合**。本文记录实测基线、由此得出的三条硬规则，以及被证伪的直觉。改动本 Skill 流程时先读这里，避免把校验加回去。

## 实测基线（2026-10-28，一次完整 PV：10:45 → 13:39）

| 项 | 实测 |
|---|---|
| 总墙钟 | 174.5 分钟（视频段第 580 秒被取消，未出片） |
| MCP 工具调用 | 177 次，工具自身耗时合计 42.9 分钟——**全部**是 `canvas_wait_tasks`（16 次 × 平均 160s） |
| 其余 176 次工具耗时 | 合计不到 2 秒；画布工具 0.01–0.12s，`canvas_get_state` 平均 0.01s |
| 空档（调用之间的等待） | 131.6 分钟，其中生成任务在跑只有 18.5 分钟 |
| **无工具、无任务在跑的时间** | **113.1 分钟 = 总时长的 65%** |
| 单轮调用间隙 | 平均 38s；前 1/3 段 36s → 后 1/3 段 59s（1.6 倍变慢） |
| 当日新增媒体 | 14 张 PNG 平均 3.4MB、最大 6.3MB；1 张 JPEG 7.6MB |

## 三条硬规则

### 1. 看图预算：一次 PV 最多三次全图审看

**目视只花在不可替代的锚点上**：角色资产图（确认身份一致）、场景母图（确认本轮选定的氛围/质感方向）、最终每个 Clip 的抽帧（核对角色、场景、动作与切点）。

- 中间候选、变体、细节图**不看**：用任务回执的宽高、比例、文件大小与状态判断是否合格；需要人眼时交给用户在画布上看，不要让 AI 逐张读。
- 确需目视时先降采样到长边 ≤1024 再读。3–6MB 原图直接进上下文会让后续每一轮都变慢。
- 审看结论一句话记下（例如"身份一致，发型偏长"），不要在同一张图上反复看第二次。

反例（本次实测）：14 张图逐张读，上下文越滚越重，单轮间隙从 36s 涨到 59s。

### 2. 调用合并：同一阶段的状态读取一次拿完

每次工具调用都要一轮 AI 推理（实测平均 38s），所以**减少调用次数比减少单次工具耗时有效一百倍**。

- 提交前一次性拿齐：`canvas_image_input_manifest`（图1/图2 顺序 + storageKey + `manifestHash`）与 `h3_get_clip_references`（活动图 storageKey 与 Picture 顺序）。核完立即提交，**同一目标只核一次**。
- 任务进度用 `canvas_wait_tasks` 批量等全部 taskId，不要用 `canvas_task_status` 逐个轮询。只有等待出错、需人工确认或用户主动问进度时才定向查询。
- 禁止"读一次 → 想一想 → 再读一次"的串联。要判断的东西先列清，一次调用取全。

反例（本次实测）：13 次 manifest、17 次 `h3_get_clip`、17 次 `canvas_get_state`、20 次 `canvas_task_status`，合计 67 次纯读取校验，光这些回合就占掉近半的空档时间。

### 3. 等待折叠：把同步等待压到「依赖层数」

同步等待本身不可避免——不知道产物就不能决定下一步。能优化的是**等几次**和**等的时候干什么**。

- **先分层再提交**：把本轮要做的事按依赖排成层。无依赖的同层任务（头图与场景图、同节点各段默认独立的 H3 Clip）**全部提交完再等一次**；等这批齐了，才提交依赖它们的下一层。等待次数等于层数，不是任务数。
- **一次等全部**：`canvas_wait_tasks` 的 `taskIds` 可以一次传多个（单次上限 32），不要一个任务等一次。`canvas_generate_image_batch` 的 `waitForCompletion:true` 就是内建的一次收口。
- **提交即返回，最后统一收口**：不需要结果就能推进的活（写第二段提示词、整理发布文案、绑参考、备封面），放在等待窗口之前或期间做。`canvas_generate_image_batch(waitForCompletion:false)` 立即拿 taskId，不阻塞。
- **提示词写作前置**：H3 各段的逐镜提示词只依赖角色与场景的**设计意图**，不依赖图像是否出完。在提交角色图之后、等待结果之前就把提示词写好，等待窗口结束时直接进入编译提交，这一段通常是整条链路里最长的纯思考工作。
- **宁可一次长等，不要反复短等**：每结束一次等待就要一轮 AI 推理（实测 38s）。用 `timeoutMs` 传小值做轮询，换来的是更多轮空转，不是更快。默认窗口（900s）通常够。
- **`timedOut:true` 不是失败**：返回里的 `pendingTaskIds` 与 `next` 就是继续等待的入口，直接按它续等原任务，不要重新提交生成。

判断标准：一次 PV 的等待次数应当接近依赖层数（典型 2–3 层），而不是接近生成任务数。

反例（本次实测）：4 张图等 4 次，其中 2 次是在任务已完成的情况下空等满窗口；修复等待逻辑后同样 4 张图只需跟随每层的完成时刻返回。

**等待的两个参数边界**（踩过才知道）：

- **客户端请求超时**：MCP 客户端默认 60 秒，`McpError -32001 Request timed out`。要等更久必须调用方自己把单次调用超时设到窗口之上，否则等待会被客户端先行打断并触发重试。窗口 ≤ 客户端超时，是硬约束。
- **等待时长的口径**：修复后（2026-10-28）`wait_tasks` 在任务完成后即返回，等待时长应≈生成时长。若观察到等待时长稳定等于传入的 `timeoutMs`，说明又退回到「等满窗口」，按缺陷处理而不是按参数调优。

### 4. 批量提交：图像候选走 `canvas_generate_image_batch`

`canvas_generate_image_batch` 支持 1–32 个 items、公共 `defaults` 与条目级覆盖，`waitForCompletion:true` 时由 MCP 内部轮询到全部终态再返回（`timeoutMs` 默认 900000ms，可到 1800000ms）。同一画布内由 Backend 串行提交以避免 revision 冲突，但**对 AI 只算一次调用**。

- 角色图的头部图/全身图/终极资产图是**有先后依赖**的三步，不能塞进一个 batch。
- 同一阶段的多候选（例如角色气质 2–3 个变体、场景 2 个氛围变体）应一次 batch 提交，用条目 `key` 区分，等全部完成再一次性比较。
- 已经确定单一目标、只需一张时，继续用 `canvas_generate_image`；**不要为了凑批量而多生成**，生成有成本。

反例（本次实测）：7 张 gpt-image 串行，从 12:10 跑到 12:52 共 42 分钟，而生成实际只占 6 分钟。

## 被证伪的直觉

- **"画布 1.7GB 库肯定拖慢操作"** → 否。生产库 `canvas_operation_batches` 2.4 万条、`canvas_command_receipts` 9.3 万条，画布工具仍在 0.01–0.12s。
- **"MCP 传输慢"** → 否。除 `wait_tasks` 外全部 0.01–0.12s；一次 PV 全程只有 1 个常驻会话。
- **"加长 wait_tasks 窗口能省时间"** → 几乎不省。它只减少往返次数与几十毫秒的调用开销，模型渲染是固定成本。
- **"独立 5s Clip 就能并行跑"** → 不能据此推断。是否并行由 H3 执行器、同节点调度与 VRAM 余量决定；通过一次 `h3_run_all_clips` 批量提交，保持片段独立，不自行并发发起多组生成。

## 视频段异常判定

H3 同配置历史平均 271s/段。**单段超过 600s 就该怀疑配置或队列**，而不是继续等：先查画幅/尺寸目标/LoRA 叠加是否超规格，再查 ComfyUI 队列里是否有别的任务。本次实测出现过 954s（3.5 倍于均值）与 922s 的图生图，都属于异常而非正常波动。

### 5. 节点纪律：一张锚图一个节点，落选当轮清

画布节点是给人看的，不是调试日志。实测因为"每次重试都新建一节点、锚图反复导入"，一次 PV 在同一画布堆到 **31 个节点**，用户直接问「画布上咋这么多图片」。一次 PV 的正常成品画布应当只有 **6 个**：官方立绘、头图、全身图、终极资产图、场景图、H3 节点。

- **导入前先查**：`canvas_inspect` 看是否已有同名/同用途的 image 节点；同一张图只导一次。重复导入会各自占一个节点且都指向同一份媒体。
- **生成会新建 config 节点**：`canvas_generate_image` / `_batch` 每次调用都新建一个 config 节点。同一步的重试、候选比较，**选定后立刻把落选节点当轮删掉**，不要留到收尾。
- **失败与取消的节点同样要删**：报错、超时、`canvas_task_cancel` 掉的任务，其 config 节点留在画布上只会变成噪音。
- **每轮收尾做一次清点**：`canvas_inspect` 数节点，超过 6 个就按上表归并。删除用 `canvas_delete_nodes(ids:[...])`，一次可传多个，连带的连线会一起删除；媒体文件仍在素材库里，不会丢。
- **删除前确认下游引用**：正在跑的 H3 任务所绑定的 image 节点不能删（会被当参考读），要删先等任务结束或先改绑。

### 6. 等待不占主线程：轮询交给后台进程

前面几节讲的是"少等几次"，这一节讲**等待期间主线程该干什么**。

反例（2026-10-28 实测，用户当场指出）：提交 H3 后用 `sleep 180` 反复轮询任务表，一次 PV 里主线程被挂住十几分钟，期间什么都不能做 —— 这等于把"工具空转"换成了"AI 空转"，性质一样。

规则：

- **提交后立刻走**。生成类任务一提交就返回 `taskId`，此时不要让主线程进入 `sleep` ＋查库的循环。
- **起一个后台看守脚本**，让它做三件事：轮询任务表到终态、产物落盘后自动抽帧/拼图、把进度写进日志文件。脚本一跑就不再占用推理轮次，也不占上下文。
- **主线程转身去做不依赖结果的事**：写下一段提示词、核对参考绑定、清画布节点、更新本 skill、准备发布文案与封面。等真需要结果时，读一次日志或产物文件即可收口。
- **子代理也能等，但更贵**：子代理会带一整份独立上下文跑一轮，适合"等完还要判断和重做"的复合任务；单纯等一个文件落地，后台进程足够，不必开子代理。
- **收口只读一次**：`work/<run>-result.json` 这类固定产物 + 一张拼好的抽帧图，主线程读这两个文件就能判断过不过，不必再逐个任务查状态。

判断标准：一次 PV 里主线程出现两次以上的轮询等待，就是编排错了。
