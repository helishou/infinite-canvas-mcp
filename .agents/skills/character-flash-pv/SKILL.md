# 人物快闪 PV

以用户指定的角色为唯一制作主体，完成角色形象、竖屏场景、按目标时长拆分的独立 H3 Clips 和平台交付。快闪 PV 每段固定 5 秒，段数由目标总时长除以 5 得出；每段独立生成，默认不开跨段上下文接续。每个项目使用独立画布；保留模型、提示词、参考图、任务和归档媒体之间的真实绑定，不能把临时工作台结果当作正式画布资产。

## 入口与约束

- 本 Skill 是自由画布短片流程，不建立剧目、分集或 Acheng 正式制作稿。画布持久编辑遵守仓库的画布数据契约；使用画布 MCP/受支持命令创建和编辑，不直写数据库。
- 编排预算（看图次数、调用合并、批量提交）与实测耗时基线见 [`references/orchestration-budget.md`](references/orchestration-budget.md)。结论先行：MCP 工具本身 0.01–0.1 秒，墙钟大头是调用之间的 AI 回合，因此**减少调用次数优先于优化单次调用**；生成侧耗时以该文件的模型基准判断是否异常。
- 调度纪律（标准批次、批量读写、批量等待、生成前门禁梯、恢复顺序）以 `../canvas-video-production-sop/references/native-mcp-operation-budget.md` 为准，本 Skill 只保留快闪专属参数与域内细节，不另立一套。快闪专属的创作简报纪律、单线快速通道与失败避坑（含连脚丝袜脚部解剖规则）见 [`references/flash-fastpath.md`](references/flash-fastpath.md)。
- 成片在剪映的踩点重音剪辑、变速吸附、调色+美颜预设、穿帮打码与 BGM 选择以 [`references/jianying-beat-sync.md`](references/jianying-beat-sync.md) 为准；该文件同时收录用户对剪辑的硬规则（不裁内容、变速上限、同镜不拆速、切点必须落锤、手动改过的草稿顺序不动、结尾必淡出）。正式成片由用户在剪映手动导出，CLI render 只出代理预览。
- 先读 `../canvas-video-production-sop/references/canvas-workspace.md` 和 `../canvas-video-production-sop/references/canvas-image-production.md` 中本次需要的小节；提交视频或恢复任务时读 `../canvas-video-production-sop/references/canvas-production-runs.md`。H3 的 Clip 参数和连续性沿用 `../canvas-video-production-sop/references/canvas-clip-production.md` 与 `.agents/rules/h3-production.md`。
- 正式画布媒体生成是有成本的动作。用户明确要求完整出片时，在本流程范围内生成角色图、场景图和按总时长计算的 N 个 Clip；“帮我设计 Skill/流程/提示词”只交付设计，不触发真实生成。
- 生成前用 `models_list` 按 image 能力查模型目录，并用 `h3_list_models({view:"entries", categories:["loras"], query:"丝袜"})` 查 H3 LoRA。直接 Canvas 生成可用精确模型 ID，不要求先连接浏览器；只有依赖工作台 UI 的 `workbench_*_get_config` 才需要网页连接。“终极资产图模型”“2.1”在目录中有精确项时直接使用；无法唯一映射时，报告可用项并只询问该映射，不静默替换。
- 不修改全局模型默认值。单次项目用覆盖参数表达用户指定值；不支持的参数不得用其他含义相近的值代替。
- 自动发布时读取同目录集成的 [`social-auto-upload`](../social-auto-upload/SKILL.md) 并遵循其平台入口；四平台的账号、参数、回执与落库核对坑见 [`references/platform-publish-pitfalls.md`](references/platform-publish-pitfalls.md)（含 `sau` 通常不在 PATH 时的定位顺序）。CLI 未安装时停下报告阻塞并保留待发布包，不全局 pip 安装、不模拟登录。用户已指定发布平台且本次要求自动发布、账号状态可用时直接执行，不重复询问授权。登录需要人工操作时保留成片与发布文案，标记该平台待登录；不得索要或保存密码、Cookie、令牌。

## 流程

### 1. 建立项目画布

1. 用 `canvas_create_project` 新建一张独立画布，标题以角色名和“快闪 PV”命名；记录真实 `projectId`，随后用它固定本会话活动画布。
2. 后续所有角色、场景、H3 节点、生成结果与最终成片都写入该画布。若创建结果未知，先按标题查询画布列表确认是否已创建，不能盲目重复创建。
3. 收集最少必要输入：角色名；用户是否提供形象参考图；若无参考图，采用随机原创设计；偏好的风格、性格/气质、场景意向和发布账号（如适用）。已有输入直接沿用，不逐项重复提问。

### 2. 设计角色并生成角色资产图

先选设计路径：

- **原创设计**：按用户描述设计角色身份、年龄观感、发型、服装、主色、辨识性配饰和整体气质。用户允许随机设计时，随机选择一套完整且自洽的方案，并先在对话中简述设计方向。
- **参考图反推**：先查看用户给的图，提取身份视觉特征、服装、配色、材质与气质；按用户要求使用当前可用的图像编辑/洗图能力形成设计参考。保留指定特征，不擅自改变角色身份。

**画风判定与漫转**（只做一次，看图判断，属允许的锚点审看）：

- 参考图是**真人实拍**→ 直接进角色资产流程，不需要转换。
- 参考图是**二次元插画 / CG 立绘 / 游戏原画 / 3D 渲染**→ 先做**漫转**再进资产与视频。理由：H3 视频模型是实拍电影摄影向，直接喂插画会掉成塑料感、五官漂移；资产图与视频首帧必须是同一画风，不能一半插画一半实拍。
- 漫转方向默认是**去二次元化**。保留清单固定为：发型轮廓与发色、瞳色与眼型、服装结构与主色、标志性配饰、纹样位置。改画风不改身份。
- **必须带官方立绘当参考图**（2026-10-28 血亏教训）：靠文字描述重建角色一定会编错——实测把"脸上有红花纹"（真图没有，纹身在右大腿）、"黑色蕾丝长裙"（真是黑色挂颈短裙+拖地黑红披风）、"小红伞"（真是巨大黑红油纸伞）、"淡蓝小花+骨白圆片"（真是红色环形束发器+白色骨质骷髅）全部写错，整条链作废重做。**没有参考图就不许做漫转**；确实只能靠描述时，必须先向用户逐项确认设计清单。
- 正确的做法是**官方立绘当参考 + 明写设计清单 + 定死"这是一张真人剧照"**（实测一次成功）：提示词开头声明"参考图是该角色的官方立绘，必须逐项复刻，不得增删替换"，紧接着列一份可核对的设计规格（发色/发型/束发器/发饰材质与形状/瞳色眼型/脸型/身上花纹的准确位置/服装款式与长度/胸前挂饰/披风/道具/配色），末尾写摄影段（85mm、f/2、柔光、胶片颗粒、真实皮肤毛孔实体发丝），并显式禁止 `anime, illustration, CG render, 3D render, doll, plastic skin, airbrushed, oversized eyes`。这样能同时拿到设计保真和真实摄影质感。
- 只给参考图、不写设计清单时，模型会被画风拽回去出 2.5D 半写实 CG；**加设计清单是把画风拉回照片的关键**，不是参考图本身的问题。
- 设计清单里最容易写错的是**纹样位置**：必须逐处确认在脸、颈、手臂还是腿上，写错一处用户一眼就看出来。
- 真人版定型后再派生的图都拿**真人锚图**当参考，不要回退到二次元图，否则下游又会被拽回插画风。
- 本地 `krea2` 的身份编辑工作流依赖 LoRA `krea2_identity_edit_v1_2.safetensors`，本机 ComfyUI 未安装该 LoRA，带参考图提交会直接 `value_not_in_list` 400 失败。要用 krea2 做漫转需先补这个 LoRA，否则走 gpt-image-2.5 或 `2.1`。
- 本地工作流会被别的重任务占住：实测 `终极资产图` 因 ComfyUI 正在跑 H3 视频而卡在 progress 0.02 长达 6 分钟不前进。提交本地工作流前先看 ComfyUI `/queue` 是否空闲；卡住且锚图有改动时直接 `canvas_task_cancel`（参数是单数 `taskId`）撤掉，别把它当成功等待。
- 用户明确要求成片就是二次元风时**不做漫转**，但要提前说明：H3 写实模型对二次元风格的保真度有限，必要时改用图生视频模型并接受风格漂移。
- 漫转产物就是后续的**身份锚图**，头图 / 全身图 / 资产图都从它派生；漫转前后要各看一次，确认是同一个人。中间的候选变体不再逐张看。

快闪 PV 制作期间，用户对流程、设定、模型或结果的纠正，须立即体现在本轮执行中，并将可复用的规则同步记录到本技能；不能只在对话里口头确认。原创或重建角色时，必须按顺序准备输入，不得跳步：**先生成头部身份/面部参考图；再生成整体全身参考图（优先以头部图锁定同一身份）；最后调用“终极资产图”模型或其精确映射工作流**。正式资产图的输入顺序固定为：**图1=头部图，图2=全身图**。用户提出的参考分工是：图1负责头部身份与面部，图2负责身体比例、服装和整体体态；如当前工作流需要其他输入形式，按配置映射并告知差异，不伪称模型收到未传入的参考。正式提交前用 `canvas_image_input_manifest` 核对图1/图2顺序、storageKey 与无阻断问题，并将返回的 `manifestHash` 传给生成工具，锁定本次实际输入。头部图、全身图或正式资产任一步未成功并核验时，不得提交依赖它的下游资产或视频。将真实归档输出绑定为角色资产；至少核对脸部、发型、服装轮廓、主色和配饰与设计方案一致。“终极资产图”可产出横幅式角色设定板，应作为角色身份参考，不能当作竖屏视频首帧。**该设定板的全身视图面部留空是设计行为，不是缺陷**（用户 2026-10-28 明确纠正）：头部身份由左侧头像面板承担，全身面板只负责服装、配饰与体态，留空避免把一张不匹配的脸糊到身体上。因此看到全身视图无脸时**判定为正常通过，不得重跑、不得改写提示词要求补脸，也不得据此判失败**；若确实需要带脸的全身视图，用头图作参考单独生成全身图，不要在设定板流程里绕。以任务回执的真实宽高核验输出构图，不能因请求了 9:16 就宣称实际输出也是 9:16；工作流可能不接受全部画幅（截至 2026-10-28 的 `2.1` 请求竖幅时实际返回 2:3），以当次回执为准，后续按回执比例规划或适配，不重复请求相同比例期待其自动改变。比例不合时调整到已支持的模型尺寸或在视频消费前执行明确的裁切/适配。失败时保留已成功的输入和资产，针对失败目标恢复，不重复提交已成功任务。

角色图是场景和视频的身份锚点。角色资产图尚未成功归档前，不提交依赖它的下游生成。

角色阶段的编排纪律：

- 头图 → 全身图 → 终极资产图是**有先后依赖**的三步，不得塞进一个 batch。
- 同一步要比较 2–3 个变体时，用 `canvas_generate_image_batch` 一次提交（条目 `key` 区分，`waitForCompletion:true`，`timeoutMs` 视画幅留足），等全部终态再一次性比较；目标已确定为单一结果时用 `canvas_generate_image`，不为凑批量多生成。
- 目视只花在正式资产图这一次，用回执的宽高、比例与状态判断中间候选；确需目视先降采样到长边 ≤1024，不逐张读原图。
- `canvas_image_input_manifest` 对同一组输入只核一次：核完立即提交，不重复核。核验结果连同 `manifestHash` 一起留在任务上下文里，后续引用它而不是重读。

### 3. 设计快闪场景并生成氛围图

围绕角色身份规划一组适合快速展示的场景与气氛节拍，例如开场剪影/登场、主体展示、收束定格。场景应有明确的色彩、光线、天气或粒子氛围，并服务角色气质；不要用无关的环境细节稀释人物主体。把场景画面提示词和氛围词分别整理，氛围词写光色、材质、运动感和情绪，不只堆泛化形容词。

用户指定“GPT 场景母图→反推”时，先用 GPT Image 生成宏大的 16:9 环境全景母图，写入具体氛围词，并按回执核实实际画幅。只有用户本轮明确要求真实实景摄影时，才把真实镜头、物理材质、自然曝光等摄影质感作为硬验收项；概念图感不合格时，可做一次有明确目标的摄影化编辑，不堆同义词反复试跑。

若用户指出“不要概念图、要真实拍摄质感”，而一次有控制的摄影化编辑仍未达标，简要说明当前差异并确认取舍。用户若选择宏大氛围优先、接受生成式电影合成感，则立刻锁定此取舍：不再追逐实拍质感，不把合成场景称为真实实拍，直接用已接受的 GPT 母图进行“2.1反推”。只有用户坚持真实摄影且提供/同意真实实景照片时，才将照片作为摄影质感主参考继续编辑；照片参考输入顺序与职责必须经 manifest 核实。

“2.1反推”必须调用当前配置的反推工作流，保留实际生成结果并核验后再绑定为场景参考；不得用普通 2.1 文生图冒充反推，也不得在母图/反推未完成时提交视频。完成后如实记录场景的目标画幅、实际画幅与质感取舍。

若用户未指定 GPT→反推，则按当前配置中精确匹配用户所说“2.1”的生图模型/工作流生成场景图，预先确认该工作流支持的画幅；按目标画幅规划留白、视觉中心与可见轮廓。无论哪条路径，均须将成功结果归档、绑定到对应场景参考，不得把角色身份图与场景图混成一个来源不明的参考。

场景侧同样按编排预算执行：视觉核验只用在母图的实景质感判定上（那是降级链的判据），反推结果按任务回执的宽高与状态核验即可；需要多个氛围变体时用 `canvas_generate_image_batch` 一次提交。

### 4. 编排 5 秒 H3 片段

基于角色资产图、场景图和场景节拍，使用仓库内的 [`h3-prompt-writing`](../acheng-director/modules/model/h3-prompt-writing/SKILL.md) Skill 规范视听提示。**每个 Clip 固定 5 秒；段数 = 目标总时长 ÷ 5。** 若总时长不是 5 的整数倍，先询问用户选择总时长，不静默取整。用户指定镜头数时严格保留；未指定时默认每秒 1 镜，即每 Clip 5 镜、每镜 1 秒。时间码必须完整覆盖 0–5 秒，每次切镜落在音乐重音上；先确定音乐节拍，再按整秒重音编排（例如 120 BPM 的 2/4 拍，每小节 1 秒、重音在小节首拍），不要后期把镜头切点与音乐重音错开。

镜头与动作组织按本目录 [`references/flash-shot-template.md`](references/flash-shot-template.md) 的**势能周期**执行：卡拍不等于有势能，每镜是一个“蓄力→重音释放”周期，切点释放上一镜蓄满的动能，禁止等距空切。每段必须独立成立：开场直接建立完整姿态与场景状态，结尾收在稳定落幅；不得依赖上一段的未完成动作、尾帧或 latent。默认关闭 Motion Context、AV latent 与 tail-frame continuation；仅在用户本轮明确要求跨段连续动作/同一连续摄影镜头时，才按需要开启相应机制。迷人/擦边尺度不预设档位，从**角色资产图**（气质、服装、丝袜等贴身元素、配饰、眼神）与**场景氛围**（光色、粒子、情绪）派生框选、慢放蓄势与近失/peekaboo 手法，末镜用带掌控感的定格收束，默认不露点且不破角色身份。每镜描述一个清晰可见动作、构图和镜头运动。

按当前 H3 Clip 入口配置以下单次运行覆盖值：

| 参数 | 本 Skill 默认目标 |
|---|---|
| 画幅 | 9:16 |
| Clip 数 | N = 目标总时长 ÷ 5；不是整数时先询问 |
| 每段时长 | 固定 5 秒 |
| 尺寸目标 | 2.0 MP |
| 连续性 | 独立生成；默认关闭 Motion Context、AV latent 与 tail-frame continuation |
| LoRA | 丝袜质感，强度 0.5 |

提交前核验 H3 当前模型能接受 5 秒、9:16 和 2.0 MP 组合；用 `h3_preview_run(view:"full")` 检查每段实际生效的参数与参考映射。`h3_get_defaults` 仅用于识别当前默认值，不代表本项目已满足目标，也不要为本项目改全局默认值。每段必须保存为独立生成，不得因共享角色或场景参考而推断需要跨段续接。若目标参数组合不受支持，先报告具体冲突和最接近的支持组合，不擅自降规格、替换 LoRA 或开启上下文模式。

在画布中准备 N 个正式 H3 Clip，绑定真实角色/场景参考并按顺序编译、翻译、检查和生成。自由画布可用 `h3_apply_video_plan` 建段；按 Ref2VA 规范改写完整提示词后，用 `h3_update_clips` 对目标 Clip 只更新 `prompt` / `timeline` 字段，避免覆盖已保存的运行参数。提交前把状态读取一次拿全：`h3_get_clip_references`（活动图 storageKey 与 Picture 顺序）与 `h3_get_clip`（已保存的运行参数）在同一阶段读完；随后用 `h3_preview_run` 对**同一 nodeIds 范围**预检，并与实际提交保持一致，独立片段统一 `skipCompleted:false`，把返回的 `planHash` 交给 `h3_run_all_clips`。若得到 `STALE_H3_PREVIEW`，该调用没有创建任务；保持原 `idempotencyKey`，按错误建议用完全相同的范围与标志重做预检，再用新 `planHash` 重提。各片段不得登记跨段 latent/tail-frame 出边；其提示词须自足，不依赖其他 Clip 的状态。

任务跟踪按[原生 MCP 操作预算](../canvas-video-production-sop/references/native-mcp-operation-budget.md)的批量等待规则执行：`canvas_wait_tasks` 一次等待全部原 taskId、事件流优先、不每分钟重复轮询，等待窗口取该文档的参考值。只有等待出错、需要人工确认或用户主动询问进度时，才用 `canvas_task_status` / `h3_get_task` 定向查看。若通过 Acheng 正式制作入口提交，遵守其翻译与编译步骤。生成后按原 taskId 跟踪状态，核对 N 段都已成功归档、时间线顺序、画幅、每段 5 秒时长、实际运行参数及段间独立性。若系统有 `ffprobe`，从归档/任务输出读取实际宽高、帧率、时长和音轨；预检尺寸只是估算（2026-10-28 实测：2.0 MP 的 9:16 预检对应 1088×1920 编码，约 2.09 MP，以当次回执为准），所以逐段报告实测值。用 scene-cut 检查或剪辑时间线复核实际切点，不能只凭提示词宣称切点符合节拍；若模型偏离整秒重音，从可用镜头动作中裁出稳定段，将每段校正为 1.0 秒，再按原音频节拍拼回，且保留原 H3 输出。若任一 Clip 的 MP4 比保存时长短，且末镜已设计为定格，则保留原画布结果，另生成带末帧停留、音频垫长/淡出的准确时长交付副本后再拼接；报告交付副本长度，不覆写 H3 历史媒体。只在能力真实提供时拼接/导出最终视频；所有分段媒体存在仍不等于已得到连续播放的成片。

### 5. 交付与平台发布

先形成可审阅交付：最终视频（若当前流程支持拼接导出）、全部原始 Clip、角色图和场景图、所用提示词与各平台发布文案。平台包至少包括标题、简介/配文、标签、封面建议和视频文件；有平台专属格式限制时从当前平台规则或连接器读取，不凭旧经验声称符合最新限制。

若已有授权的官方/受支持发布连接，且用户明确要求自动发布：逐个平台提交内容，读取成功回执和发布链接；失败仅对该平台报告并保留可重试的发布包，不重复发布已成功的平台。四个平台分别确认：小红书、B站、抖音、视频号。只有收到平台成功回执才标记为“已发布”。

各平台的登录方式、易错参数（如 B站分区 tid）、误标/误发后的补救与落库核对方法，见 [`references/platform-publish-pitfalls.md`](references/platform-publish-pitfalls.md)。提交前按它核对账号状态与必填参数，不凭记忆传值；分区、声明这类不可程序化纠正的选项尤其要先核对。

若没有发布连接或授权：交付待发布素材包，逐个平台说明当前阻塞原因和下一步；不索要或存储密码、Cookie、令牌，也不尝试模拟登录绕过平台权限。

## 验收回执

完成时用紧凑清单报告：

- 画布名称与 ID。
- 角色设计路径及角色资产的归档状态。
- 场景图与氛围设计的归档状态。
- 所有 Clip 的状态：数量、画幅、每段 5 秒时长、尺寸目标、独立生成状态、LoRA 名称与强度；区分“请求参数”与“实际生效参数”。
- 最终视频是否已导出，以及交付物（成片、全部原始 Clip、角色图、场景图、提示词、各平台文案）的实际落盘路径；无路径即视为未交付。
- 四个平台逐项列出发布状态：成功回执、发布链接、创作者后台落库核对结果；三者缺一不标“已发布”。
- 未完成项、精确阻塞原因（含 `sau` 未安装、账号待登录这类可复现阻塞）。
