# 一致性的「事前防范」架构（提示词装配 + 资产锚点 + 连续性计划）

> 主用于：剧情设计 → Clip 视频（`canvas-video-story-design` → `canvas-video-clip-production`）

SKILL.md「段间色温漂移」与「多段项目的正确组织」的展开。解决的不是「检测出漂移」，而是**让漂移不可能发生**。

## 为什么必须事前建：漂移是构造性的，不是运气

**「逐段独立重写提示词」这个做法本身就会生产漂移。** 实测：四段提示词里**本该逐字相同**的冻结内容，相似度实测值：

| 冻结内容 | 跨段相似度（修复前） |
|---|---|
| 场景光位段 | 0.10 ~ 0.33 |
| 角色外观段（S01 vs S04） | **0.06**（且 S04 整段变回了中文） |
| 防字幕措辞 | 各段各异（S01 缺 `subtitle`/`watermark`，其余有） |
| `<Picture N>` 引用 | 四段全固定 `[1,2,3,4]`，与实际 6/7/7/8 张参考对不上 |

同一个光位规格被独立写了 4 遍、措辞全不同 —— 4 次生成当然收敛不到一起。**这不是「写得不够细」，是「没有单一事实来源」。**

判据：把每段提示词按六段式切开，对同名小节做两两相似度。**本该恒等的小节低于 1.0 就是架构问题**，改措辞治不了。

**提示词不该被「写」，该被「装配」。** 修完后同样的检查全部为 1.0000（见「校验清单」）。

## 一致性的四层模型（决定该在哪一层动手）

| 层 | 问题 | 事后能补救吗 | 手段 |
|---|---|---|---|
| **影调** | 色温/曝光/影调统一 | ✅ 纯数学，确定性 | LAB 统计对齐（`ImageColorMatch+` / `scripts/lab_bstar.py` 量测） |
| **身份 + 空间** | 同一张脸、同一个房间 | ⚠️ 靠参考图条件化 | 角色四视图 + 场景图作参考 |
| **姿态状态** | 站立 ↔ 坐姿这类**状态** | ❌ 事后无解 | 必须条件化（尾帧接续 / 边界连续声明） |
| **动作因果** | 「站起来」这个**过程**本身 | ❌ 事后无解 | 一个镜头拍完，或落在合法切点上 |

**排查顺序必须自上而下**：先量影调（便宜、确定性），再看身份/空间（有无参考图），最后才谈姿态与动作。**影调没对齐时下游全部测量都被污染** —— 在视频层做色彩匹配等于用第二次生成去补第一次生成的错。

## 一、Bible（单一事实来源）

一份 `project-bible.json`，四块**冻结内容**逐字冻结，其余字段按段不同：

```json
{
  "frozen_blocks": ["identity", "scene_and_light", "negative", "color_baseline"],
  "rule": "frozen_blocks 必须在每段提示词中逐字出现，禁止改写、翻译或省略",
  "identity":      { "su-wan": {"subjectIndex":1,"pictureIndex":3,"subjectId":"su-wan","en":"<Subject 1> is …"}, "shen-zhao": {…} },
  "scene_and_light": { "nodeId": "…", "en": "<Picture 1> is the deep-night apartment living-room environment. … The warm-yellow table lamp … is the ONLY key light source. …" },
  "negative":      { "en": "No subtitles, no captions, no on-screen text of any kind, … no watermarks, no logos, … No fifth person appears." },
  "color_baseline": { "reference": "scene", "storageKey": "image:…", "L": 23.81, "b": 4.72 },
  "storyboard":    { "S02": [ {"picture":4, "r":1, "c":1, "nodeId":"image-…", "storageKey":"image:…", "shotId":"S02-1", "time":"0.0-1.0s"} ] },
  "boundaries":    { "S01->S02": "CONTINUE", "S02->S03": "CUT", "S03->S04": "CUT", "S04->END": "END" }
}
```

要点：
- **Bible 用英文写**（官方规范是英文，且混语言本身就是漂移的一种表现 —— 实测 S04 的 `subject_definitions` 整段退回中文）。
- `identity` 逐条绑定 `subjectIndex` / `pictureIndex` / `subjectId`，把「谁是谁、第几张图」写死，不靠装配时现推。
- `color_baseline` 直接存 LAB 数值，供三级资产对齐共用（宫格 / 洗图 / 超分）。
- `storyboard` 把「第 N 张参考 ↔ 第几格 ↔ 哪个镜号 ↔ 哪一秒」一次写死 —— **这是「提示词漏了分镜描写」的结构性解法**，不靠人记得写。

## 二、装配器（不是生成器）

```
bible 冻结块 ─┐
分镜清单(自动派生) ─┼→ 逐字段拼装 → prompt
剧情(shots 表) ─┘
```

- **冻结块整段拼接**，不做任何改写、摘要、翻译。
- **分镜清单由代码从真实参考清单派生**，保证「有几张分镜参考就有几条 `<Picture N>` 说明」。每条写清：`<Picture N>` 是该镜的 keyframe、对应哪个镜号与秒数、镜头型式、要复现的构图、这一镜要完成的动作。**一句笼统的「keyframe reference for the shot sequence」不够** —— 实测只写这一句时，5 张分镜参考里有 4 张从未被提及。
- **剧情段逐镜装配**：每个 `[Shot N]` 写 时间 + 镜头型式 + 构图 + 动作 + 微表情 + 对白（`<d>[Chinese] …</d>`），并在段内明确「本镜是单一连续机位，内部不切」。

### 三道自动校验（装配完立刻跑）

1. **覆盖校验**：`prompt` 里出现的 `<Picture N>` 编号集合必须覆盖 `1..实际参考数`。缺任何一张就报错，不放过。
2. **冻结块完整性**：四个冻结块必须**逐字**出现在成品里（`block in prompt` 精确子串，不是模糊匹配）。
3. **跨段相似度报告**：对同名小节两两算相似度，**非 1.0000 即失败**。

### ⚠️ 两个装配器陷阱

- **`negative` 必须是最后一块。** 段间漂移最容易发生在「末行」—— 任何插在负向清单之后的东西都会把它挤走。加校验时把「末行是否恒等」也纳入（这是本会话抓到排序 bug 的位置）。
- **不要手动追加尾帧锚点。** 尾帧锚点（`<Picture 1> is the opening frame…`）由运行器 `appendTailFramePrompt` 在**运行时**注入，且它会把原有 `<Picture N>` 整体 +1。装配器若也手动加一条，会与运行器的重编号**叠加成双重位移**，且破坏「负向清单在最后」的顺序。**装配器只管静态内容，运行时注入留给运行器。**

## 三、边界连续性计划（事前声明，不是事后补救）

**段间断裂之所以刺眼，不是因为断了，而是因为在「不该断的地方」断了。** 硬切观众完全接受 —— 前提是切在动作的间隙。所以每个边界必须由剧本决定，不能由模型自由发挥：

| 边界 | 声明 | 含义 |
|---|---|---|
| 同段动作延续 | `CONTINUE` | 开尾帧续接（开关标在**前一段**上） |
| 剧本切点 | `CUT` | 不做续接，允许硬切 |
| 片尾 | `END` | — |

落库方式：`CONTINUE` 的边界把 `tailFrameContinuation=true` 写在**前一段**。

⚠️ **但要先看清执行链**：`resolveClipContinuation` 的前置是 `chained = parent.input.runFromCurrent === true && segmentIndex > 0`，而 `h3_run_clip` **不带 `runFromCurrent`**。所以**逐段跑时这两个开关写了也不生效** —— 见 SKILL.md「续接的触发条件在整条运行链上」。事前声明只是必要条件，不是充分条件。

## 四、段内镜头数预算（段内跳变的直接原因）

**7 秒段默认上限 3 镜（每镜 ≥ 2.0s）。** 实测每段每镜秒数：

| 段 | 镜数 / 时长 | 每镜 | 判定 |
|---|---|---|---|
| S01 | 3 / 7s | 2.33s | ✓ |
| S02 | 4 / 7s | 1.75s | ✗ 超载 |
| S03 | 4 / 7s | 1.75s | ✗ 超载 |
| S04 | 5 / 8s | 1.60s | ✗ 超载 |

**超载的后果是段内姿态跳变**：每次切镜模型都重新推导场景状态，镜位越密、重推次数越多、漂移机会越多。实测**唯一合规的 S01 也是动作最准的一段**。

**合并口径（保持总时长不变）**：把相邻、同主体的镜头并成一条长镜，合并点落在**原有镜头边界**上（不臆造新时点），并在提示词里补「本镜为单一连续机位，内部不切」。实测把 4/4/5 镜合并为 3/3/3 镜后，**全部台词逐字保留（8 句 8 对）、时间轴仍从 0 连续到 duration**。

对照口径：若不愿并镜，另一条路是**拆段**（总时长会涨）。合并与拆分都要先摆给用户选，不要自己决定。

## 五、色彩基准锚点（资产准备环节）

**宫格是 N 次互相独立的图像生成调用，没有共同色彩基准** —— 这是段间色温漂移的源头（实测四张宫格 `b*` = +3.9 / +4.5 / +6.9 / +5.7，对应视频被放大到 +2.4 / +4.8 / +8.6 / +2.8）。

纪律：**宫格生成后对齐 → 洗图后对齐 → 超分后对齐**，三级都拉回同一张基准图（通常取场景图）。基准值写进 Bible 的 `color_baseline`。

- 量测用 `scripts/lab_bstar.py`；对齐用 LAB 空间均值/标准差匹配（等价 `ImageColorMatch+` 的 `factor=1.0`）。
- **容差**：`b*` ±1.5、`L*` ±3.0。超出即视为偏离。
- **对齐必须发生在生成视频之前。** 资产层面的偏差会被 H3 放大（实测约 2 倍），到视频层再修就是用第二次生成补第一次的错。

### 走画布工作流做对齐时的槽位约束

`ImageColorMatch+` 需要**两路输入**（`image` 待修 + `reference` 基准），而 `fields` 是参考图注入的**唯一入口**（`image-dispatcher.ts` 按 `fields` 里 `type:"image"` 的字段顺序把 `references[i]` 映到第 i 个 image field）。所以：

- `custom/krea2改图.json` **只有 1 个 image field（node 8）** —— 单图槽，接不了「待修 + 基准」两路。
- `custom/krea2双图编辑.json` **有 2 个 image field（node 3 + 4）** —— 现成的双图载体。

⚠️ **不要把基准图硬编码进工作流 JSON 的 `LoadImage` 默认值**：画布上传参考图时会覆盖 input 目录里的同名文件，硬编码会失效或被换成别的图。基准图必须当作**一个 reference node** 传进来。

**编辑 `~/.infinite-canvas/workflows/custom/*.json` 时的两条纪律**：

- **用 `curl http://127.0.0.1:8188/object_info/<NodeClass>` 拿它的真实输入名与类型**，不要信旧版 UI 工作流里遗留的 `choices` / `widgets_values` 形状。输入名以 schema 为准（例：`ImageColorMatch+` 的必需项是 `image` / `reference` / `color_space` / `factor` / `device` / `batch_size`，`factor` 范围 0~1、默认 1.0；`Krea2EditGroundedEncode` 的 `image_b` 是 optional，tooltip 写着「2nd reference (subject)… vision blocks in training order: scene, subject」）。
- **不要用 `magick` / python-magick 这类工具程序化增删节点** —— 它们会重写节点的全部 ID 与连线，把工作流结构搞坏。**用 Python 直接读 JSON、改 `inputs`、写回**，节点 ID 保持原样。
- 工作流改完**不需要重启任何进程**：`WorkflowStore.get()` 每次从磁盘读，改了即生效。

（若要在 MCP 侧把对齐做成可批量、可复用的能力，纯数学实现比走扩散工作流更合适：确定性、秒级、不受 ComfyUI 排队影响 —— 这正是「影调层用确定性手段」的应用。但只要它还要跑 KSampler，就是在用生成式手段做本该纯数学的事。）

### 走 krea2 双图工作流做调色：参考图顺序与提示词结构都是硬约束

用 `custom/krea2双图编辑.json`（模型名 `krea2` + 传 ≥2 张参考图即自动路由到它）做调色时，**两件事必须同时对，缺一不可**：

**① 参考图顺序 = `[被调色的图, 调色板来源]`**，即把**要保留**的那张放 Image 1。`Krea2EditGroundedEncode` 的 `image` / `image_b` tooltip 写的是 `vision blocks in training order: scene, subject` —— 该工作流训练目标是「把 subject 合成进 scene」，顺序颠倒等于把主体与场景的角色互换。

**② 提示词必须给出可执行的提取与映射规则**，不能用关系型抽象描述。实测对照（同 seed、同参考图、同宽高比，唯一变量是提示词）：

| 提示词写法 | 结果 `b*` | 对基准（+4.72）的偏差 |
|---|---|---|
| 原图（待调色） | +11.66 | +6.94 |
| 「match its color temperature to the first image」这类抽象关系句 | +18.74 | **+14.02（反而更黄）** |
| 显式调色板提取 + 三段映射 | +7.61 | **+2.89（改善 58%）** |

**反模式（实测会更糟）**：让扩散模型「把 A 的色调对齐到 B」这种**抽象关系指令**。该 LoRA 训练目标是 identity edit，它会把待调色图里的暖偏**当成主体特征一并保留并放大** —— 所以越「对齐」越黄。

**有效结构**（三段缺一不可）：
1. **显式排除构图**：`Use Image 2 as the color reference only — ignore its composition entirely.` —— 这句是关键，缺了会把参考图的构图也带进来。
2. **显式指定提取目标**：`Extract the color palette from the stripe in Image 2.` —— 把抽象的色彩匹配变成具体操作。
3. **三段式色调映射**（给可执行规则，不是「感觉像是这样」）：最暗 → 阴影/黑位/深调；中间调 → 中间调/肤色/环境光；最亮 → 高光/天空/轮廓光。
4. 收尾重申 `Preserve every detail of Image 1 — composition, faces, subjects, framing — unchanged.`

⚠️ **本条的验收只覆盖了色温（`b*` 实测）与输出尺寸；「构图是否真的被保住」尚未核实** —— 抽帧识图曾提示人物左右位置可能漂移，但读图通道随即不可用、未能复核，且当时只有 n=1。**用这条配方时，构图必须单独抽帧核对**，不要因为 `b*` 变好就默认画面没变。要坐实需要用固定 seed 跑一组「含/不含 ignore its composition」的对照。

## 校验清单（改完装配链后逐条跑）

1. 覆盖校验：`引用 <Picture N> 数 == 实际参考数`。
2. 冻结块逐字存在（四个块分别 `in` 检查）。
3. 跨段同名小节相似度 **全部 1.0000**（含「末行」这一项）。
4. 台词逐字：从成品里抽 `<d>[Chinese] …</d>` 与原稿做**排序后全等比较**（不是模糊匹配）。
5. 段内镜数 ≤ 3 且每镜 ≥ 2.0s。
6. 资产色温：所有宫格/洗图/超分相对基准在容差内。

**第 3、4 项是这批唯一能提前发现问题的两道闸** —— 实测第 4 项曾抓出「8 句只装配进 7 句」（另一次是舞台提示「无台词，只有开门声」被误当台词，属判据误报，需人工看一眼）。

## 装配链暴露出的三个真 bug（同类问题的征兆）

这些不是「实验噪声」，是设计缺陷在数据上的表现 —— 见到同类征兆就往这三处查：

1. **末行不一致** → 有东西插在 `negative` 之后（本节「装配器陷阱」）。
2. **台词少一句** → 合并镜头时把一组里多句台词只取了一句；合并逻辑要校验「组内每句台词都进了成品」。
3. **镜数校验读了旧文件** → 生成器读 A 文件、校验器读 B 文件（合并前后两个 shots 文件），校验结果与成品脱节。**校验器必须读装配器实际用的那个源文件。**
