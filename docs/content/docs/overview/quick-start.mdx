# Quick Start

Normal use requires the Backend and the `web/` frontend. The Backend integrates Agent and MCP endpoints; the separate Canvas Agent on port 17371 is a compatibility proxy for older clients.

## Prerequisites

For native use, prefer **Node.js 24 LTS**; **22.x from 22.16.0** is also supported. Do not use 23.x. Backend relies on transaction-state APIs in built-in `node:sqlite`. Install Git and Corepack, then install all workspaces from the root with the pinned **pnpm 12.12.1**. No separate database service is needed.

```bash
node --version
corepack --version
corepack pnpm --version
```

If Corepack is absent, run `npm install --global corepack` and reopen your terminal. Repository scripts invoke Corepack, so installing only a global pnpm is insufficient. Commands here use `corepack pnpm` directly; `corepack enable` is unnecessary.

Basic canvas use needs no Python, GPU or Codex login. Video tools need FFmpeg/FFprobe; Acheng compilation needs Python 3.10+, Git and an activated runtime; local generation needs your ComfyUI/models; sidebar chat needs the Codex CLI version declared by the shared package. See [Docker Deployment](/docs/overview/docker) for image dependencies.

## Run locally

```bash
git clone --depth 1 --recurse-submodules https://github.com/helishou/infinite-canvas-mcp.git
cd infinite-canvas-mcp
corepack pnpm install --frozen-lockfile
corepack pnpm run dev
```

Open `http://localhost:3001`.

`corepack pnpm run dev` builds the official plugin registry and `canvas-agent/dist` before starting either service and does not clear existing services. Root-level `dev:backend`, `dev:web`, and `dev:services` also build those shared assets first; direct workspace `dev` commands do not. Backend `dev` and `dev:watch` reload after source changes when tasks, confirmations, Agent turns and writes are idle. Use `dev:once` for a single run. Rebuild shared Agent sources to update the watched `dist` outputs.

For daily production, stop the existing Backend while it is idle, then run `corepack pnpm run start:backend`. This builds the shared Agent and Backend and serves the compiled Backend through the persistent public endpoint. Source edits and later builds leave the running process on its loaded version. Repeat the startup procedure to apply updates. Keep using the existing frontend, or run `corepack pnpm run dev:web` in another terminal. Existing data directories and connection settings are reused.

| Address | Purpose |
| --- | --- |
| `http://localhost:3001` | Local development frontend |
| `http://127.0.0.1:17370` | Backend, `/agent`, and `/mcp` |
| `http://127.0.0.1:17371` | Optional legacy compatibility proxy |
| `http://localhost:3000` | Docker gateway with a same-origin Backend proxy |

Use `dev:services` when the compatibility proxy is needed. Windows-only `dev:local` clears old services on those ports before starting three processes; it is not a liveness probe.

Use source mode or the full Compose deployment for the base stack; configure model services, ComfyUI and the director engine separately.

## Installation and startup troubleshooting

- For slow downloads, use an HTTPS shallow clone, or download the basic source ZIP from GitHub. ZIP archives exclude submodules; director runtimes still need Git setup. The project does not switch to third-party mirrors automatically.
- Use `corepack pnpm` for repository commands so Corepack selects pnpm 12.12.1 from the root `package.json`; if Corepack is unavailable, install Corepack as described above. Use Node 22.x from 22.16.0 or prefer 24 LTS.
- The repository maintains one workspace lockfile. From the repository root, run `corepack pnpm install --frozen-lockfile`; do not install from an individual workspace or create a second lockfile.
- If `canvas-agent/dist/...` is missing, run `corepack pnpm --filter @basketikun/canvas-agent run build` or use the root startup commands. A failed build is not a Backend connection error.
- If `safe-delete state lock timeout` comes from host-injected `NODE_OPTIONS`, investigate the host injection and Vite cache-cleanup conflict. Startup scripts preserve `NODE_OPTIONS` and do not automatically disable deletion guards or other host protections.
- Codex CLI is optional. For sidebar Codex chat, run `npm install -g @openai/codex@0.160.0` and sign in. Canvas, MCP, and local ComfyUI can skip this installation. The model picker uses the catalog returned by the Codex app-server that Canvas Agent actually starts.
- Shot-cut detection on a video node runs `backend/workers/detect_video_scenes.py` from Backend and needs `scenedetect-headless` from `backend/workers/requirements-video-shot-detection.txt`. Install it into the Python that Backend uses (`python -m pip install -r backend/workers/requirements-video-shot-detection.txt`), or point `SCENEDETECT_PYTHON` at an interpreter that has it. Without it the endpoint returns 503. Docker images already include it.

## Optional Python environments

These steps apply only to Python features. Reuse an existing environment when suitable; do not reinstall Python/ComfyUI for basic canvas use or overwrite an existing `backend/venv`.

If a new environment is needed, create it from the repository root and invoke its interpreter directly, without activating shell scripts:

```powershell
# Windows; skip creation when reusing an environment
py -3 -m venv backend/venv
# Install only features you use; these requirement lists can also be installed separately
backend/venv/Scripts/python.exe -m pip install -r backend/workers/requirements-video-shot-detection.txt -r backend/workers/requirements-style-transfer.txt
```

```bash
# Linux/macOS; skip creation when reusing an environment
python3 -m venv backend/venv
backend/venv/bin/python -m pip install -r backend/workers/requirements-video-shot-detection.txt -r backend/workers/requirements-style-transfer.txt
```

Shot detection and style transfer prefer explicit `SCENEDETECT_PYTHON` / `STYLE_TRANSFER_PYTHON`, then `backend/venv`, then system Python. Acheng uses a separate `ACHENG_PYTHON`; set it to an **absolute path to an existing interpreter**. Otherwise it discovers system Python rather than automatically selecting `backend/venv`.

Add FFmpeg/FFprobe to the Backend process PATH, or set `FFMPEG_PATH` / `FFPROBE_PATH`. Check `ffmpeg -version` and `ffprobe -version` in the terminal that starts Backend. The H3 Motion Context main path uses Node/sharp/FFmpeg and does not need the old Python worker's dependencies.

Initialize the Git submodule and validate/activate the cloned Acheng commit:

```bash
git submodule update --init -- .agents/skills/acheng-director
corepack pnpm run acheng:update -- --local
corepack pnpm run acheng:status
```

`acheng:update -- --local` validates and activates a runtime; run it while generation, chat and compilation are idle. JSON compilation/auditing uses the standard library; install the submodule's `requirements.txt` only for YAML input or PNG tooling. Runtimes default to `.canvas-runtime`; back up the actual directory if using `INFINITE_CANVAS_ACHENG_HOME`.

## Data and upgrades

The default Backend directory is `~/.infinite-canvas/`, but runtime configuration can change data and media locations. Check the actual `/data-dir` response and configuration; back up original media alongside the SQLite media index.

Before migrating an existing older SQLite database, the Backend creates and integrity-checks a `runtime.sqlite.pre-schema-*.sqlite` snapshot. Backup failure blocks migration. Newer or invalid schema versions are refused; deleting the database is not a recovery method. Snapshots exclude media and do not replace full backups. Preserve browser pending edits and conflict drafts. Storage schema is 53 with a minimum direct-upgrade baseline of 52. Older databases/backups must first use the previous Backend to reach 52. After new writes, repair forward instead of overwriting edits with an old backup.

## LAN access

Defaults retain local listening and origin validation. If you decide to expose the service to your own LAN devices, change only `listenHost` to `0.0.0.0` in the actual data directory's `backend.json`, and add the frontend's full origin, such as `http://192.168.1.10:3001`, to existing `origins`. Preserve the existing URL, token, and local origins; do not use `*`.

After reloading the relevant service, open the server's port-3001 frontend on the other device and enter the server Backend URL `http://192.168.1.10:17370` and existing connection key in connection settings. Loopback addresses on that device refer to itself. Allow the required firewall ports on the host, and do not expose them directly to the public internet.

In development, Vite proxies `/media`, `/events`, and `/agent` on the frontend origin, avoiding direct browser SSE connections to port 17370 for a local Backend. Whether a system proxy truncates direct SSE connections depends on the environment.

## Run with Docker

Run `docker compose up -d --build` to start the Web gateway and Backend. Open `http://localhost:3000`, use `http://localhost:3000/api` as the Backend URL, and enter the persistent Backend key in connection settings. Install optional models and CLIs separately; a named volume stores business data. See [Docker Deployment](/docs/overview/docker) for configuration, first connection, backups and limitations.

## Deploy with Vercel

The root `vercel.json` builds the static Web app and its shared plugins, not a Backend. To connect a separate Backend on Vercel/Render, set the public `VITE_BACKEND_URL` build variable (for example, `https://canvas.example.com/api`) and add the page origin to the Backend allowlist. Users enter their connection key in the UI. Canvases, assets, and structured settings remain stored in the Backend.

## First-time setup

- Connect to the Backend first. API models require channel URLs, keys, and models; local ComfyUI requires its service and workflows without an OpenAI API key. Editing canvases alone needs no model endpoint.
- Open `/prompts` to fetch prompt repositories directly from the browser and cache them in memory.
- Configure WebDAV if you want to synchronize canvases, assets, and generation history across devices.

Canvas projects, My Assets, generation records, and structured settings use the local Backend SQLite database as their authority. Media is stored in the Backend media directory. Channel keys are stored in that database and used by the selected executor; canvas generation tasks are created and recorded by the Backend.
